## Visão do módulo (vai para `docs/product/PRODUCT.md`, tarefa 1)

Resultado esperado: **"O jogo da semana acontece sem confusão de lista e com times equilibrados."** Caso de referência: vôlei misto de sexta (quantidade de homens e mulheres varia), rotação normal com levantador fixo.

| Termo     | Significado                                              |
| --------- | -------------------------------------------------------- |
| Dono      | quem criou o grupo                                       |
| Jogador   | qualquer participante                                    |
| Membro    | joga sempre; entra pelo link de membro                   |
| Reserva   | joga quando sobra vaga; entra pelo link de reserva       |
| Convidado | qualquer pessoa, quando a lista abre para todos          |
| Fila      | quem confirmou com a lista cheia; sobe se alguém desiste |
| Jogo      | a ocorrência semanal do grupo                            |

| #   | Entrega                                                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| E1  | Grupo + link de membro + jogo da semana + confirmação + fila + cancelar jogo                                                                     |
| E2  | Reservas + abertura da lista em camadas (membros → reservas → aberto), configurável                                                              |
| E3  | Divisão de times: manual, por nível, por nível + função; espalhar gênero; 1 levantador fixo por time                                             |
| E4  | Resultado por partida, com a escalação de cada partida                                                                                           |
| E5  | MVP configurável (desligado / votação / escolha do dono)                                                                                         |
| E6  | Ajuste automático de nível com rating de equipe (OpenSkill/Weng-Lin), só por resultados; MVP não entra no nível; o dono pode corrigir e congelar |

Limite conhecido (E1), também registrado no PRODUCT: duas desistências ou remoções simultâneas de quem está dentro podem notificar a mesma pessoa da fila e pular outra. A lista fica certa; só a notificação falha.

## Decisões de modelagem

| #   | Decisão                                                                                                                                                                                                                                                                                                                                                             | Por quê                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **Jogos recorrentes são calculados, não agendados.** O "jogo atual" é a primeira ocorrência (`weekday` + `time` no `timezone` do grupo) com `startsAt + 3 h > now`. Ela só vira item no banco na 1ª escrita (1ª confirmação ou cancelamento). Antes disso a api devolve o jogo "virtual" com a lista vazia                                                          | sem cron/EventBridge (nenhum recurso novo de infra); nada acontece sozinho na abertura da lista na E1; jogo sem ninguém não gera item              |
| D2  | Jogo identificado pela **data local** (`YYYY-MM-DD`) nas rotas. Entidade `GAME#<id>` (via `newEntity`) + lookup único `LOOKUP#GAME#<groupId>#<date>` → `{ id }` com `attribute_not_exists(PK)`; perdeu a corrida → relê consistente (mesmo padrão do `findOrCreateByEmail`)                                                                                         | sem GSI e sem id montado na mão; duas confirmações simultâneas no jogo virtual não criam 2 jogos                                                   |
| D3  | Status: `scheduled` (antes de `opensAt = startsAt − listOpensHoursBefore`, 1 a 144 h) → `open` → `in_progress` (de `startsAt` a `startsAt + 3 h`: lista visível, sem confirmar, desistir nem cancelar) → depois disso o atual é o da semana seguinte. `cancelled` vale até o fim da mesma janela                                                                    | a lista do jogo seguinte abre no mínimo 24 h depois do início do atual (168 − 144), então nunca há dois jogos atuais; sem histórico na E1          |
| D4  | **Fila é implícita**: a presença é uma lista ordenada (`LOOKUP#GAME#<gameId>#ATTENDANCE`, `SK=<confirmedAt>#<userId>`). Posição < `slots` = dentro; o resto = fila. Desistir apaga a presença; quem estava na posição `slots` sobe sozinho                                                                                                                          | nenhum campo de status para manter em sincronia, nenhuma escrita de "promoção"; ordem de confirmação é a própria chave                             |
| D5  | Presença = entidade `ATTENDANCE#<id>` `{ gameId, userId }` + lookup de ordem (D4) + lookup único `LOOKUP#GAME#<gameId>#ATTENDANCE#USER#<userId>`, os três numa `TransactWriteItems`. Confirmar de novo é idempotente; reconfirmar depois de desistir vai para o fim. O dono só está na lista se confirmar                                                           | regra do CLAUDE.md (entidade + todos os lookups juntos, valor único com condição)                                                                  |
| D6  | Notificação de promoção (desistência **ou remoção**): depois do `Delete`, se quem saiu estava dentro, relê a lista (consistente) e notifica quem agora está na posição `slots − 1`, se ele estava na fila antes. Tipos novos `waitlist_promoted` e `game_cancelled` via `notify()`; o cancelamento notifica confirmados e fila, exceto o dono                       | usa o `NotificationService` que já existe; título/corpo em pt-BR (exceção já registrada no CLAUDE.md)                                              |
| D7  | Grupo `GROUP#<id>`: `name, sport, weekday (0–6), time (HH:mm), timeZone (mesmo nome do campo do `User`; padrão: o fuso do perfil do dono, ou America/Sao_Paulo se ele não tiver; IANA via `TimeZoneSchema`), location, slots (2–50), listOpensHoursBefore, ownerId, inviteToken`. Esporte = enum curto em contracts (`volleyball`, `soccer`, `basketball`, `other`) | contrato fechado; o web traduz o nome do esporte via i18n                                                                                          |
| D8  | Membro sem entidade própria na E1: dois lookups, `LOOKUP#GROUP#<groupId>#MEMBER` (`SK=<userId>`, `{ id: userId }`) e `LOOKUP#USER#<userId>#GROUP` (`SK=<groupId>`, `{ id: groupId }`), com `attribute_not_exists`. O dono entra como membro na transação de criação                                                                                                 | "meus grupos" e "membros do grupo" sem GSI; entrar duas vezes é idempotente; papel do dono sai do `ownerId`                                        |
| D9  | Convite: `inviteToken` aleatório (`crypto`) no grupo + lookup `LOOKUP#GROUP#INVITE#<token>` → `{ id }`. "Gerar outro" = uma transação: `Delete` do lookup antigo, `Put` do novo, `Update` do grupo. Gerar outro **é** invalidar o anterior                                                                                                                          | regra de campo com lookup mudado; o dono revê o link atual a qualquer hora (token não é segredo de login)                                          |
| D10 | Não-membro recebe `GROUP_NOT_FOUND` (404) em qualquer rota do grupo; ação de dono por membro → `GROUP_NOT_OWNER` (403 com `{ error }`)                                                                                                                                                                                                                              | não vaza a existência do grupo; o 403 com corpo não dispara a renovação de sessão do web                                                           |
| D11 | Fuso: helper puro em `api/src/lib/zoned.ts` com `Intl.DateTimeFormat` (sem dependência nova). Todo cálculo de data recebe `now` injetado                                                                                                                                                                                                                            | testável com relógio fake; `startsAt`/`opensAt` saem em UTC (`...Z`) e o web formata no fuso do usuário com `formatDateTime` (ADR 0006; plano 005) |
| D12 | **Remover membro** = uma `TransactWriteItems`: `Delete` dos 2 lookups de membro + troca do convite (D9) + se o jogo atual está `scheduled`/`open` e ele tem presença, `Delete` da presença e dos 2 lookups dela. Com o jogo `in_progress` a presença fica. Depois, promoção como em D6. O removido não é notificado; o dono não pode se remover                     | perde o acesso e a vaga de uma vez; trocar o link impede voltar pelo link antigo sem criar lista de bloqueio; lista congelada durante o jogo       |

## Interface do bloco 2 (api `groups`; para os testes)

Um módulo, `api/src/modules/groups/`, com dois services (`group.service.ts`, `game.service.ts`) e dois repositórios (`group.repository.ts`, `game.repository.ts`). Os testes de service usam repositórios em memória que implementam as interfaces abaixo.

**Dependências** (o mesmo objeto para os dois services): `createGroupService(deps)` e `createGameService(deps)`, com `deps = { groups: GroupRepository, games: GameRepository, users: UserDirectory, notifications: Pick<NotificationService, 'notify'>, now?: () => Date }`.

## Interface do bloco 3 (web; para os testes)

O guard do router vira uma função pura em `web/src/app/guard.ts` (o `router.ts` só faz o `loadMe` e chama a função). Assim o caso 3 (parte web) é testável sem montar o router.

| Export                                                                           | O que faz                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `safeRedirect(value: unknown): string`                                           | destino interno seguro: texto que começa com `/` e não com `//` → ele mesmo; qualquer outra coisa (ausente, array, `https://...`, `//evil`) → `/`                                                                                                                                                                                                                      |
| `guardDecision({ to, isAuthenticated, needsProfile }): true \| RouteLocationRaw` | `to = { name?, fullPath, query, meta: { public? } }`. Regras, nesta ordem: (1) rota pública: login com sessão → `safeRedirect(to.query.redirect)`; senão `true`. (2) sem sessão → `{ name: 'login', query: { redirect: to.fullPath } }`. (3) `needsProfile` e não é o perfil → `{ name: 'profile', query: { welcome: '1', redirect: to.fullPath } }`. (4) senão `true` |

Fluxo do caso 3 na web, de ponta a ponta: `/join/<token>` sem sessão → login com `redirect=/join/<token>` → depois do código, se a conta é nova, perfil com `welcome=1&redirect=/join/<token>` (o `LoginPage` passa o `redirect` adiante) → ao salvar, o `ProfilePage` vai para `safeRedirect(redirect)` → a página do convite aceita e troca para `/groups/<id>`.
