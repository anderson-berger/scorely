### `/rule <correção>`: classificação

| Ordem | Pergunta da skill                                   | Destino                                                                                                                                    | Prova                                                                                                                               |
| ----- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1     | Dá para verificar por máquina? (preferência máxima) | regra do Biome (se existir uma pronta) ou teste em `checks/`, com a regra em uma linha no `.claude/rules/<área>.md` apontando para o check | o check falha com a violação plantada e passa no código atual (se falhar no código atual: lista as violações e não corrige sozinha) |
| 2     | Tem motivo/trade-off ("fizemos X porque Y")?        | `docs/decisions/NNNN-slug.md` + linha no índice                                                                                            | o índice cita a decisão                                                                                                             |
| 3     | Senão, é convenção                                  | `.claude/rules/<área>.md` certo (cria com `paths:` se a área for nova) ou o `CLAUDE.md`, se for global                                     | não há duplicata (procura antes de gravar)                                                                                          |

Saída: uma linha dizendo "classifiquei como X, gravei em Y". Uma correção pode gerar 1 + 2 (check + motivo). O `CLAUDE.md` instrui: "quando o dono corrigir algo, ofereça `/rule`".

### Relatório do revisor (formato fixo, ≤ 40 linhas)

`Veredito` · `✅ Respeitou` (plano/regra → evidência) · `❌ Violou` (regra → `arquivo:linha`) · `⚠️ Precisa de você` (decisões tomadas sem estar no plano, mudanças fora do escopo, contrato alterado) · `Testes` (casos do plano × testes existentes; testes alterados depois do passo 3) · `npm run check` (resultado).

## Riscos gerais

- **Isolamento do test-writer é por instrução e por ordem, não por sandbox.** Em tarefa nova, a implementação ainda não existe. Em tarefa que altera um módulo existente, a garantia é a instrução + `tools` + o revisor conferir que os testes usam só a interface pública. Se a tarefa 1 mostrar que hooks distinguem o subagente, um `PreToolUse` em `Read` endurece isso.
- **Revisor é o mesmo modelo.** A independência é de contexto, não de "opinião". O risco cai com o checklist fixo e com checks automáticos (o que é máquina não depende do revisor).
- **Contexto de regras por `paths:`** depende da versão do Claude Code (tarefa 1 valida, `CLAUDE.md` aninhado é o plano B).
- **Hook de commit lento:** o `npm run check` inteiro pode levar minutos; aceitável, porque só roda no commit.
- **O `pre-commit` pode ser pulado:** `git commit --no-verify` passa por cima (é escolha sua), e um clone fora do devcontainer só tem o hook depois de `git config core.hooksPath .githooks` (o README vai dizer isso).
- **Excesso de ADRs/regras com o tempo:** o `/rule` procura duplicatas antes de gravar; as regras de área devem caber em ~60 linhas cada (acima disso, dividir a área).
